# 项目开发、文档维护、流程复用与技能更新指南

本指南适用于持续维护的软件项目，也适用于与 Codex 等开发代理协作的场景。
核心做法是：用源码与验证建立事实，用项目文档保存知识，用流程减少重复工作，用 skills 帮助代理稳定执行已经验证的方法。

本文是跨项目方法，不替代 Bless 的具体约定。
维护 Bless 文档时还应阅读[文档贡献指南](documentation.md)；构建、测试、发布和基准实验则以仓库当前的实现与相应参考文档为准。

## 一、明确各类信息放在哪里

| 载体 | 主要责任 | 典型内容 |
|---|---|---|
| 源码与配置 | 定义实际行为 | 接口、默认值、边界、依赖、构建与部署配置 |
| 测试与 CI | 验证可检查的要求 | 回归测试、集成测试、并发检查、构建与发布门禁 |
| 项目文档 | 解释行为、理由与证据 | 架构、使用指南、设计取舍、审查、实验记录、路线图 |
| 可执行工具 | 自动完成重复且确定的操作 | 链接检查、数据处理、环境检查、发布辅助 |
| Skills | 指导代理选择和执行工作流程 | 适用场景、关键约束、验证选择、文档入口、交付要求 |

这些载体互相补充。
Skill 不能代替项目事实，文档不能代替实际验证，CI 通过也不能证明未覆盖的行为正确。

当信息冲突时，先辨别是在讨论“实际行为”还是“预期行为”。
实际行为由当前源码和运行证据核验；预期行为还需要结合用户要求、接口承诺和设计约束。
发现偏差后决定修复实现、修正文档，或明确限制，不能机械地把当前代码中的缺陷当成正确规范。

## 二、推荐的工作循环

### 1. 明确目标与范围

确定这次工作是审查、实现、排障、实验还是发布，并明确预期产物。
审查任务交付发现与证据；实现任务交付修改和验证；发布任务还需要明确源版本、产物及目标。

开始前检查分支、提交、工作区和项目约束，保留他人的未提交改动。
区分已经授权的工作与额外动作，不将一次构建授权扩大成发布授权，也不对已经明确授权的常规步骤反复请求确认。

### 2. 建立当前事实

优先阅读相关源码、配置、构建规则、测试入口和已有文档，避免依赖旧参数表、历史行号和完成百分比。
记录必要的基线：提交、运行环境、依赖、输入和验证方法。
范围较小的修改不必生成大报告；跨模块审查或实验需要更完整的基线。

### 3. 完成工作并选择验证

围绕行为变化选择最小但有意义的检查。
测试应验证实际要求和失败模式，避免只重复实现逻辑。

明确证据层次：

- 静态审查：根据代码关系确认风险或行为，说明推断依据。
- 局部复现：验证一个具体缺陷，说明提取代码、桩接口和环境限制。
- 单元验证：验证模块或函数，说明是否链接生产实现。
- 集成验证：验证真实模块交互、依赖和运行路径。
- 端到端验证：从用户、对端或部署环境观察结果。

某一层通过不能自动替代更高层的证据。
根据风险和环境选择需要的层次，不要求每个小修改都执行全部检查。

### 4. 同步项目文档

更新被这次修改影响的使用方式、接口、配置、架构理由、限制和验证状态。
保持技术事实有明确的维护位置，其他文档通过链接引用，减少重复表格。

新增主题时更新导航；移动文件时检查引用；涉及多语言时同步关键行为与边界。
译稿可以保留更详细的讲解，但不能继续沿用过时参数和完成状态。

### 5. 判断是否值得复用

先判断新经验属于一次性结果、可重复流程，还是可以自动执行的操作。

- 一次性结果写入审查、问题记录或实验报告。
- 稳定流程写入项目流程文档，或提炼到 skill。
- 重复且确定的操作优先考虑脚本或 CI；skill 负责指导何时运行及如何解释结果。

重复出现、跨多个任务有用，或者虽不常见但遗漏代价较高的方法，都值得提炼。

### 6. 更新 skill 并验证

如果此次工作证明现有 skill 遗漏了关键约束、错误路由或使用了过时命令，应及时更新。
若流程仍在探索，先记录证据，待结论稳定后再固化。

完成格式、引用和脚本验证后，检查实际使用效果。
规范校验只能证明文件结构合规，不能证明指导方法有效。

### 7. 交付具体结果

交付说明至少回答：完成了什么、为什么这样处理、如何验证、还有哪些限制，以及当前提交或发布状态。
进度说明应区分已完成的检查、正在执行的任务和仍未开始的工作。

## 三、如何维护项目文档

### 按职责组织

可根据项目规模采用如下结构，不必为了目录形式创建空文件：

```text
docs/
  overview.md          # 项目入口与导航
  guides/              # 使用、配置、部署、排障
  design/              # 架构约束与设计理由
  reference/           # 接口、构建、测试、审查与实验
  contributing/        # 开发和维护约定
```

规模较小的项目可以合并目录。
关键是读者知道去哪找信息，以及每个主题有明确维护位置。

### 区分持续更新与历史记录

| 文档类型 | 更新方式 |
|---|---|
| 当前接口、配置、使用指南 | 随实现更新，保持当前有效 |
| 设计理由 | 更新有效约束；保留仍有价值的取舍解释 |
| 审查与实验报告 | 固定日期和版本，保留当时证据 |
| 路线图与问题状态 | 持续更新，并链接修复提交和验证结果 |

后续修复不能悄悄抹去历史审查，也不能让历史报告中的“待修复”永久代表当前状态。
为关闭问题提供新的证据入口。

### 让记录可复查

重要问题或实验建议记录：基线版本、输入与触发条件、步骤或命令、结果、影响、限制、下一步或验收条件。
日志过大时保存产物并记录摘要；临时目录可以用于工作，但不能成为长期文档的唯一证据。

## 四、什么内容适合成为 skill

一个有用的 skill 应使代理在特定任务中作出更准确的选择，而不是增加一份泛泛的手册。

适合写入：

- 明确的触发场景与适用范围。
- 项目特有、容易遗漏的约束。
- 任务类型与验证入口的对应关系。
- 必须核验的资源所有权、并发、协议或发布边界。
- 获取最新事实的源码和文档入口。
- 已验证的执行顺序、失败后的停止条件和交付要求。

不宜直接写入：

- 一次失败的完整终端日志。
- 未验证的猜测或个人临时做法。
- 会频繁变化的版本、代码行号、固定阈值与完成百分比。
- 与入口文档重复的大段参数表。
- 已由系统规则提供的泛化要求。
- 超出用户任务范围的自动发布、对外通信或环境修改授权。

例如，“某次测试发现批次数量不一致”属于审查记录；
“检查分配容量、填入数量、循环边界与提交数量在裁剪后是否一致”适合写入数据面验证 skill。

## 五、什么时候更新 skill

| 情况 | 建议 |
|---|---|
| 经过实际验证的流程发生变化 | 随任务及时更新 |
| 使用 skill 时发现漏检、错误命令或错误路由 | 修正造成错误的具体部分 |
| 新发现尚未稳定，存在多个未验证方案 | 先写项目文档，暂不固化流程 |
| 参数、版本或代码位置变化 | 更新事实来源；尽量让 skill 引用来源而非复制数据 |
| 相同做法在多个任务中重复出现 | 提炼共同流程，判断是否需要脚本 |
| 内容增长但任务差异明显 | 拆分 skill 或将条件性细节移到参考文件 |
| 某个约束已失效 | 删除或修正，并检查依赖它的引用和流程 |

不需要每次开发都改 skill。
更新应由实际变化或使用证据驱动，避免经验堆积成越来越长的检查清单。

## 六、skill 的结构与保存方式

常见结构为：

```text
skill-name/
  SKILL.md              # 必需：名称、描述、关键流程
  agents/openai.yaml    # 可选：界面名称、简介、调用示例
  references/           # 按需读取的详细流程
  scripts/              # 有重复执行价值的工具
```

入口保持精炼，详细条件流程按需读取。
只创建确实需要的文件；新增脚本应运行验证。

对于已采用项目分组的本机布局，可以使用：

```text
~/.codex/skill-groups/<project>/<skill-name>/
~/.codex/skills/<skill-name> -> 对应实际目录
```

这是本机组织方式，不是所有环境的强制要求。
若环境指定其他技能根目录，以其配置为准。

共享项目流程、脚本与关键知识宜放在仓库中，以便版本控制和团队复用。
本机 skill 应尽量引用这些资料，避免只有某台机器掌握关键流程。
若需要共享 skill 本身，也应明确其版本、来源和安装方式。

## 七、避免文档与 skill 同时过时

每类知识确定一个主要维护位置：事实在源码/参考文档，历史结果在报告，执行方法在流程/skill，可自动检查的要求在测试/CI。

Skill 应提示代理重新核验当前来源，而不是假设其创建时的状态仍然有效。
历史问题可以作为检查线索，但不能永久写成“项目一定存在这个缺陷”。

维护时可以沿着影响链检查：

```text
行为或接口变化
  -> 测试与验证入口
  -> 用户及开发文档
  -> 使用这些入口的工具与流程
  -> 对应 skill
```

不要求所有节点每次都修改；逐项判断是否受到影响即可。

## 八、协作、权限与敏感信息

明确区分准备产物和执行外部动作。
构建、生成文档、准备发布树通常可以先完成；发布、替换远端历史或修改线上环境应依照用户授权与环境权限执行。
Skill 不应凭自身文字扩展授权，也不应把每次常规修改都变成新的确认流程。

准备发布时记录源版本、目标、产物身份、验证结果和失败处理条件。
遇到远端并发修改或 lease 失败，应先核验变化，避免自动改为无保护覆盖。

不要把凭据、令牌、私有日志或客户数据写入可复用 skill。
共享前检查仓库路径、内部地址、实验配置和报告内容是否适合目标受众。

## 九、建议的交付检查

根据任务风险使用，不必机械执行全部项目：

- 目标行为是否达成，是否保留无关工作区改动？
- 验证是否覆盖真正改变的生产路径？
- 是否明确已执行结果、静态判断和无法验证的部分？
- 当前文档与历史记录是否分别维护？
- 新经验是否足够稳定，值得加入流程或 skill？
- skill 是否包含过时事实、重复资料或无依据的权限扩张？
- 文件、引用、元数据和新增脚本是否完成必要检查？
- 提交、推送、部署或发布状态是否准确表达？

## 十、可直接用于协作的请求示例

日常开发：

> 完成这项修改，并同步相关文档和必要验证。如果形成了经过验证、可复用的新流程，也更新对应 skill；一次性发现先记录到项目文档。

项目审查：

> 审查当前项目，区分已复现问题、静态风险和未验证范围，记录版本与证据，形成按优先级排列的修复建议。先保持代码不变。

流程整理：

> 根据本次任务的实际执行结果提炼流程，保留关键约束与验证入口。动态参数引用项目文档，不将未验证方案固化成规则。

技能复查：

> 对照当前仓库和最近的实际任务，检查这些 skills 的触发范围、命令、约束和引用是否仍有效，修正有证据支持的问题。

发布准备：

> 准备指定版本的发布产物，完成所需验证，列明源版本、目标和发布步骤；执行外部发布时遵循本次授权范围。

文档迁移：

> 以当前仓库为依据吸收旧文档的有效讲解，重新核验参数、阈值和完成状态，更新导航并检查引用。

推荐从轻量做法开始：先把当前工作做对并留下证据，再将稳定的方法提炼成可复用流程。
项目增长后，逐步增加自动化和技能分工。
