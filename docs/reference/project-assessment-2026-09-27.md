### A01：TX mbuf 所有权

位置：[worker.c](../../src/worker.c)，`worker_func_tx_only()`，基线行号 238、348、423、467；[pacing.c](../../src/pacing.c)，`pacing_submit()`。

mbuf 在循环开始前批量分配，循环中持续使用同一组指针。提交成功的 mbuf 交给 PMD；未提交的部分在循环内释放，但下一轮没有重新分配或补充这些槽位。
因此成功路径可能修改驱动仍持有或已回收的对象，失败路径可能访问已释放对象，导致报文损坏、重复释放或内存池损坏。

修复应明确构造、提交成功、部分提交和失败路径的所有权，并覆盖每轮重新取得可用 mbuf 的行为。
验证必须包含多个连续批次、部分发送和零发送；版本号 smoke 与软件计数增长不能证明生命周期正确。

### A02：TX 数组长度

位置：[worker.c](../../src/worker.c)，`worker_func_tx_only()`，基线行号 203–238。

局部 `batch` 被限制到 2048，并进一步限制到剩余 `num`；指针数组按该局部值分配。
随后 `bless_alloc_mbufs()` 使用原始 `conf->batch` 填入指针。
`num=1, batch=32` 会出现一个槽位对应 32 次填入；原始批次大于 2048 时也存在同类数量不一致。

最小程序已触发 ASan 堆越界。修复应在分配、填入和循环边界中统一使用实际批次，并验证零值、有限数量和上限裁剪。

### A03：QUIC 长度边界

位置：[proto_quic.c](../../src/proto_quic.c)，`quic_build_initial()`，基线行号 79–150；[config_bless_ether.c](../../src/config_bless_ether.c)，MTU 解析。

配置允许 `mtu=46`，扣除 IPv4/UDP 头后传给 QUIC 构造器的容量为 18 字节。
构造器先写入默认约 30 字节的头部，再用 `max_len - 已写长度` 裁剪 TLS 长度，结果下溢为 65524。
原函数局部复现已报告从 TLS 临时数组越界读取；真实 mbuf 中还会产生超出声明载荷范围的写入。

修复应在任何写入前检查最小容量，对可变 CID 和长度编码逐步检查空间，并明确协议最低长度的配置约束。
构造失败路径释放 mbuf 的责任也应与调用方统一，避免调用方再次释放。

### A04：熵采样槽位并发

位置：[entropy.h](../../include/entropy.h)，`entropy_sampler_commit()`；[entropy_stats.c](../../src/entropy_stats.c)，消费者读取循环。

写入端以普通赋值更新样本结构体，再 release 发布索引；读取端 acquire 索引后直接读取槽位。
这能发布已经完成的写入，但不能防止生产者回绕后覆盖消费者仍在读取的槽位。
覆盖数量统计没有为槽位建立读写保护，可能出现数据竞争和混合样本。

修复需要明确槽位的并发协议，例如避免覆盖未读槽位或使用能保证 C 内存模型下无数据竞争的快照设计。
新增压力测试应专门触发多次回绕和慢消费者，并验证指标样本完整性；现有 runtime-control TSan 通过不代表该环安全。

### A05：CI 镜像发布条件

位置：[ci.yml](../../.github/workflows/ci.yml)，`docker` job 与 `Push to ghcr.io`。

工作流监听主分支 push 和 PR；Docker job 没有依赖主测试 job，推送步骤也没有限制为主分支 push。
在权限允许的同仓库 PR 中，可能推送未经合并的 `latest`；fork PR 则可能在该步骤因权限不足失败。
具体可写权限还取决于仓库设置，本次未查询设置或实际发布记录。

应保留 PR 构建验证，将发布限制到明确的受信事件，并要求相关测试任务成功。

### A06：QUIC 有效性声明

位置：[proto_quic.c](../../src/proto_quic.c)，Initial 构造和 TLS 模板。

构造过程缺少完整包号、Initial AEAD 加密和头部保护；CRYPTO 中包含 TLS record，而不是仅携带 TLS 握手消息。
当前构造也未实现客户端 Initial 数据报的 1200 字节最低长度要求。
因此代码和文档中的“有效 Initial”表述超过实现证据。

应明确其作为特定报文或异常流量生成的边界，或补齐协议实现并增加独立解析/对端互操作测试。
协议依据：[RFC 9000](https://www.rfc-editor.org/rfc/rfc9000.html)与 [RFC 9001](https://www.rfc-editor.org/rfc/rfc9001.html)。

### A07：逐字节重放

位置：[proto_udp.c](../../src/proto_udp.c)，IPv4 `packet_id` 使用 `rte_rand()`；[README](../../README.md)，固定种子的重放声明。

自有 per-core PRNG 的种子不能自动控制所有随机来源。UDP 的 `rte_rand()` 路径已经足以使普通生成路径的逐字节相同承诺缺乏依据。
开启时延测量时的时间戳也需要单独界定。
现有确定性检查比较熵输出，不能替代报文字节比较。

应统一受种子控制的随机来源，定义允许变化的字段和运行条件，并使用抓包比较验证承诺；实现前应收紧文档表述。

### A08：抖动与等待边界

位置：[define.h](../../include/define.h)，`random_delay_jitter()`；[pacing.c](../../src/pacing.c)，`pacing_submit()`。

`base + 随机偏移 - jitter` 使用无符号运算。当 `jitter > base` 且取到较低随机值时，会下溢为极大延迟；`2*jitter+1` 和后续周期转换也需要检查溢出。
等待截止时间的忙循环没有退出状态检查，异常或过大的截止时间可能使停止无法及时生效。

应验证或饱和处理参数与转换运算，并给等待提供取消检查。此次未在完整数据面复现停止挂起。

### A09：有限数量与多 worker 停止

位置：[worker.c](../../src/worker.c)，`effective = nb_tx`、`num -= sent`、`worker_check_state()`。

初始批次会按 `num` 裁剪，但后续迭代未按当前剩余数量裁剪。
例如完整提交条件下，`num=100, batch=32` 可提交 128 个包。
任一 worker 的数量耗尽还会设置共享退出状态，其他 worker 可能提前停止。

应定义 `num` 是全局还是每 worker 配额，再验证精确边界、多个 worker 和部分提交。

### A10：Compose 实验拓扑

位置：[docker-compose.yml](../../docker-compose.yml)、[左端配置](../../conf/config-hs-left.yaml)、[右端配置](../../conf/config-hs-right.yaml)。

配置依赖 `bless-left0` 与 `bless-right0` PCAP 接口，但 Compose 只创建普通 bridge 网络，没有建立这些命名接口或将它们移入容器命名空间。
`NET_ADMIN` 权限不会自动创建所需拓扑，因此示例中的直接启动步骤不足以完成实验。

应提供明确的拓扑准备与清理流程，或使 Compose 与实际接口配置一致，并验证双端 RX、抓包和握手结果。

## 测试与性能结论

现有 CI 包含编译器矩阵、单元测试、sanitizer、模糊测试、TSan、软件 PMD smoke、依赖审计和 Docker 检查，工程基础较完整。
主要不足在覆盖边界：完整 sanitizer 二进制只执行 `--version`，没有覆盖 TX 主循环；部分辅助测试使用局部重实现；TSan 没有覆盖熵采样槽位。

`net_null` 下的计数增长、熵活动或指标可访问，只能证明对应路径有活动，不能证明 mbuf 所有权、报文内容或对端接收正确。
应增加面向生产发包路径的集成验证，并以抓包、RX 和实际生命周期检查补充软件指标。

此次没有重测吞吐或时延，也没有据此推翻历史测量值。
核心正确性修复后，应按[基准方法](benchmarks.md)重新测量受影响路径，在解释性能时同时提供环境、报文正确性和接收证据。
